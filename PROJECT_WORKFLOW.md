# Project workflow

Current task-allocation path: three-step saved requirements/uploads → explicit Lead preference → separate exact proposal approval → Planning workforce revision → optional saved BA/CTO/PM refinement → per-task model review/override → exact workforce approval → real dependency-bound tasks → separate repository-change approval → existing restricted baseline/patch/review/QA → existing Phase 5 final review/package/release/client gates. Planning completion is not software delivery.

Requirements support bounded TXT/MD/CSV/JSON and main-text DOCX, provenance and versioned replacement/removal. Approved documents become project-scoped semantic sources. Engineering can also save authenticated read-only GitHub branch/commit/tree/dependency/README/test findings. These metadata-only entries cannot run coding; a separate managed checkout is required. No model installation, paid fallback, generated PR or release is authorized by import or staffing approval. Historical missing-feature statements below are superseded by IMPLEMENTATION_STATUS.md and TEST_REPORT.md.

Start at Home → New project: Describe, Choose AI, Review. Owner-bound versioned drafts and parsed uploads persist before any inference; submission queues a live requirement, never an approved Project. Unavailable AI waits or permits a separately authored manual proposal. Exact existing proposal approval creates the Project. Five workspace stages expose requirements, staffing planning, engineering, QA/review and delivery through existing controls. Publication, release and closure approvals remain separate. PROJECT_WIZARD.md describes formats, recovery and remaining scope.

[Owner walkthrough](docs/user-guide.md) covers intake, revision, alternatives and exact approval. [API reference](docs/api.md) lists endpoints.

Implemented path: requirement → persisted analysis/specialists/CFO → alternatives → versioned owner approval → project/milestones → dependent planning tasks → artifacts. Generic specialist assignments create scoped document tasks. Missing provider configuration waits durably.

Coding has a distinct approved scope: baseline in restricted runner → validated patch/diff → one/two independent reviews under configured diversity → independent QA evidence. A failed/empty baseline blocks code generation. Fixture reviewers cannot certify changes and actual Docker execution is unverified here.

Final security/CTO/PM acceptance, automatic repair, staging/demo, client feedback/acceptance, release handoff and support lifecycle automation remain incomplete. Planning/artifact completion never means a software project has been delivered.
